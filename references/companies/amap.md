# 高德（Agent / 后端，出行 + 交易场景）

> 样本：1 份录音（高德 agent 二面 ~56min，缺开场）。**零八股、零算法，但有 44% 时间是代码 Review**。样本量 1，结论为"该场次画像"。

## 一句话画像

**考"线上跑起来会怎么坏、坏了你怎么知道、知道了你怎么修"——是可观测性与故障纵深，不是概念广度。**

## 风格特征

- 口语化极高，常自我更正用词（"稳定性，呃，不是稳定性吧，就是可靠性吧"）。
- **答案规格施压**：不人身攻击，但会"没听清，你总结一下具体是什么"；直接给反例击穿方案（"两次请求的 requestID 不一样，你锁不住吧"）。
- **换域验证**：chat → 电商订单 → 酒店预定 → 业务代码，四域连打，看是"套路"还是"理解"。
- **长时间静默不催**：代码 Review 环节给候选人 16+ 分钟读码，面试官全程不打断。
- **零正反馈**：不评价对错，收尾一句"行，那你今天先这样"，直接问"多久能到"。
- **升维收尾**：bug 讲完必补一句"从 design 的角度，这个类该怎么设计"。

## 考察重点

1. **Agent 可观测性指标分层**：可用性（健康状态/限流）、体验（首字时延/端到端时延）、质量（任务通过率/满意度）、成本（token）、链路（工具调用成功率/重试成功率）。
2. **幻觉工具调用的归因顺序**：工具选错 → 参数填错 → 上下文污染 → 工具定义过近/描述不清晰 → 校验型 Agent 是否给对信息 →（最后才）模型本身。**优先怀疑工程侧**。
3. **长任务（跨天）可靠性**：checkpoint 粒度（每个子状态后）、内容（上下文/节点变量/各 Agent 中间结果/会话 ID）、宕机后调度中心恢复、C 端进度可感知（taskID）。
4. **幂等与去重**：从"请求级去重"到"业务级幂等"的跨越；能否区分"用户真想下两单"与"系统重复提交"。
5. **RAG 深度**：双路召回→RRF→rerank（cross-encoder 才有 query-doc 交叉注意力）；问到训练即止（"不是特别清楚"可接受）。
6. **场景化 Agent 闭环**：意图识别/澄清 → 工具编排 → 混合检索（结构化字段精确 + 描述性字段向量）→ 事务（并发锁、确认按钮、支付回调）→ 幂等。
7. **业务代码工程直觉**：库存边界（`amount <= 0`）、失败分支未 return、DB/Cache 双写不一致与读写顺序、消息通知最终一致性补偿、类职责边界。

## 高频题（原话样本）

- "如果一个 Agent 产生了幻觉的工具调用，你会从什么地方找？"
- "最终结果不符合预期，你会怎么排查？"
- "设计一个跨天的长任务，从 C 端和服务侧的整体链路怎么设计？可靠性和宕机恢复怎么保证？用户怎么感知进度？"
- "核心讲讲状态恢复这一块，你会怎么做？"
- "如何保证相同任务不会因为失败重试/网络重试/用户连点而重复提交？"
- "你这个幂等的 key 是什么？两次请求的 requestID 不一样吧？"
- "换一个场景，电商下单：怎么区分用户下了两个相同订单，还是系统重复提交？"
- "双路召回之后，通常还会做什么？rerank 怎么训练？"
- "通过 chat 帮用户完成酒店预定，你先梳理一下：工具都有哪些、编排怎么做？"（允许画图）
- "亲子房、游泳池这种非结构化属性，怎么检索出来？"
- "找一下这个 service 里有问题的地方。"（给真实代码，静默 review）

## 危险信号

- 指标只会罗列"准确率"，没有分层、没有成本/时延/链路成功率。
- 幂等只会"加 Redis 锁"，说不出 key 怎么设计、两次请求为何不同。
- 场景题只会线性说"意图识别→检索→下单"，缺工具清单、并发、资金安全边界（Agent 不能替用户支付）。
- 代码 Review 只找出表面 bug（空指针/边界），说不出 DB/Cache 一致性、职责边界。

## 话术速取

- 收窄范围："你们核心讲讲状态恢复这一块。"
- 要求结构化："你先整理一下，工具都有哪些，编排怎么做。"
- 允许画图："你可以说说、画画。"
- 换域加压："再换一个场景，电商就行。"
- 施压复述："没听清，你总结一下具体是什么。"
- 升维："从 design 的角度，这个类该怎么设计？"
